## 0. What this document tested first, before designing anything

Per the operator's explicit instruction ("test this ruthlessly... if it dies, kill it and name what beats it"), Section 1 is a kill-test of the "view from above" wedge against what incumbents actually allow *today*, checked live rather than assumed. The verdict changes the design. Read this before (a)–(g), because it determines what (a)–(g) can honestly promise.

### 1. The "view from above" wedge — kill-test

**The hypothesis (operator-considerations §Hypotheses 1):** a unified layer where a user sees their existing TikTok/Instagram/YouTube feeds inside this platform, via official APIs, OAuth, and portability law.

**What I checked, live, this session:**

- **Instagram/Meta Graph API `[VERIFIED 2026, source: Meta developer docs summaries via Elfsight/Storrito/Bluehost, cross-checked]`**: the Instagram Basic Display API — the one that let a *personal* account grant read access to its own feed — reached end-of-life **December 4, 2024** and no longer functions. What remains is the Graph API, scoped to **Business and Creator accounts only**; a personal account cannot authorize third-party feed access at all today. oEmbed ("Meta oEmbed Read," replacing the old oEmbed system as of April 2025) embeds a **single public post you already have the URL for** — not a scrollable feed, not a following-list aggregation, and not stories or private accounts.
- **TikTok `[VERIFIED 2026, source: TikTok for Developers docs summary, scrapfly/taggbox secondary sources]`**: the Display API returns the **connecting user's own** profile info and content (their own uploads), for building things like "embed my TikTok on my website" — it is not a mechanism for pulling a user's For You feed or their followed accounts' videos into a third party. TikTok's embeddable player covers individual public videos by URL, same shape as Instagram's oEmbed. A separate Research API and a Data Portability API exist but are scoped to research access and user-initiated export, not live third-party feed rendering.
- **YouTube `[UNVERIFIED this session — not re-checked live, carried from training knowledge, flagged accordingly]`**: the YouTube Data API v3 is comparatively the most open of the three — OAuth lets an authorized app read a user's own subscriptions and playlists and the embeddable player covers any public video by ID. This is the one leg of the tripod I did not re-verify live and should be treated as the weakest-confidence claim in this section.
- **GDPR Article 20 (portability) `[VERIFIED 2026, source: gdpr-info.eu / EDPB position via search]`**: the right is to receive *data you provided* in a structured, machine-readable format, and to have it transmitted to another controller "where technically feasible" — it is an **export right, not a live-sync API mandate**. The EDPB's own position (per search) draws the line at raw inputs/activity logs (portable) vs. derived/inferred outputs like a ranking or recommendation (not portable). Nothing in Article 20 obligates Meta, ByteDance, or Google to expose a continuous, near-real-time feed to a third party. This closes the "portability law fills the API gap" escape hatch the hypothesis implicitly leaned on.
- **DMA interoperability `[VERIFIED 2026, source: DMA developer portal / practitioner summaries via search]`**: Article 6(7) interoperability applies to OS/hardware-adjacent features, and the *messaging* interoperability track (Article 7, WhatsApp/Messenger 1:1 text and images since March 2024, group/voice/video phased through 2025–2027) is the DMA's actual social-interoperability lever — it does not require Meta or ByteDance to open a general third-party feed-rendering API for Instagram or TikTok content. Feed-level interoperability is not currently a live legal obligation.

**Verdict, against the three criteria the phase prompt sets:**

| Criterion | Verdict |
|---|---|
| (a) useful with zero network | Survives only for the narrowed version below — a link-first hub is useful alone; a "your friends' feeds inside our app" version was never going to satisfy this criterion anyway, since it needs your friends' accounts connected first. |
| (b) more fun than the incumbent tonight, not in theory | Fails for the full hypothesis: Instagram personal feeds and TikTok followed-feeds are not obtainable via official channels today, so there is no "tonight" version of a unified scroll to be more fun than — it cannot be built at all without violating the operator's own legal red line (official APIs + OAuth only, no scraping). |
| (c) network accretes without "joining" | N/A — moot once (a)/(b) fail for the full version. |

**The hypothesis dies in its literal form.** A unified layer that renders a user's Instagram and TikTok *feeds* (the content their friends and follows post) inside this platform, live, via official channels, is **not buildable today** for two of its three target platforms. It was never a scraping-vs-not question — it's that the read surface for personal/social content simply does not exist as a third-party grant on Instagram or TikTok in 2026, full stop, license or no license.

**What survives, narrowed, and what replaces the rest — the wedge this design actually uses (Section 4/(d) below):**

1. **Your own content, fully, everywhere you're authorized.** OAuth to your *own* YouTube (subscriptions, playlists, uploads) and your own Instagram/TikTok Business or Creator account (if you have one) is real and legal — this powers cross-posting *out* (Section 4), not feed aggregation *in*.
2. **Any single public post/video, embedded cleanly, anywhere.** oEmbed for Instagram, TikTok's embeddable player, and YouTube's embed are all real, official, and available today for a **URL a person already has** — this is the actual mechanism behind the wedge, not a unified scroll.
3. **Portability export, batch not live.** GDPR/CCPA-style export tools (Instagram's "Download Your Information," TikTok's export, Google Takeout) genuinely exist and genuinely produce your own historical data — useful for a one-time import into this platform when someone leaves an incumbent, not for an ongoing mirrored feed.

So "view from above" is **kept as a name, killed as a mechanism, replaced by a narrower one that is actually legal and buildable**: not *"see your incumbent feeds inside our app,"* but *"bring any single thing you already have a link to — or already own outright — into a room you control, cleanly, with no tracking pixel riding along, and react to it with real people."* That is what Section 4 calls **the drawer**, and it is the actual wedge this design commits to. Everything below is built on the narrowed, verified version, not the original hypothesis.

## (a) The platform design — architecture, governance/charter, economic model

### Name (working): **Commons** — a shared home, not a feed. (Placeholder; not load-bearing to the design.)

### Architecture, in one paragraph

Commons is a **link-and-room** system, not a ranked feed. The atomic unit is a **room**: a bounded space (a household, a project, a street, a book club, a grief group, a hobby) that a small number of people build together — closer to a shared notebook + a shared doorway than to a public square. Inside a room, people drop **drawers** (see wedge, above): a link to anything public anywhere (oEmbedded cleanly, no incumbent tracking pixel, no autoplay-into-the-next-thing), a note, a photo, a plan, a meeting time, a piece of their own cross-posted work. There is no global ranked feed of "everything," anywhere in the product — the only ordering primitive that exists is **reverse-chronological within a room you're already in**, which is a structural choice explained in (b)/(c), not a policy promise. Discovery across rooms happens through **invitation and search**, never through a recommendation engine surfacing you to strangers or strangers to you (Section (c), pattern 6).

### Governance / charter — the legal form, not a manifesto

Per operator decision 3 ("Form... must be real legal documents... not a manifesto"):

- **Steward-ownership trust** (a purpose trust modeled on the Purpose Foundation / Ecosia / Patagonia "never for sale" structures, or a US perpetual-purpose trust) holds 100% of the voting equity of the operating entity. The trust deed states, as binding terms, not aspirations: (1) the platform is never sold to an investor, acquirer, or advertiser; (2) surplus revenue funds operations and a capped reserve, never distributed as profit to a founder or shareholder class; (3) the covenant (this tournament's manifesto document) is incorporated by reference as a binding operating charter that amendments require a supermajority of trustees *plus* a public comment period, not a simple board vote; (4) an independent steward seat (not appointed by the founder) holds veto power specifically over any change to data-sale, ad-insertion, or engagement-ranking clauses — the single most-abused lever in the dossier.
- **No investors, per operator decision.** The build is funded by (i) founder/operator capital contribution at formation, (ii) a below-market loan facility (program-related investment from a foundation, or a steward-ownership-friendly lender — this is a real, existing financing category for steward-owned companies, not invented for this design) `[UNVERIFIED — I have not checked current lender terms live this session; flagging as a design assumption, not a verified fact]`, and (iii) subscription revenue from month 1 (Section (a)/money mechanics below). No equity round, ever, structurally — the trust cannot issue equity to a new owner because it does not hold equity to sell; it holds an irrevocable purpose commitment.
- **A religious/teaching vehicle, if it ever exists, is legally separate**, per operator decision on institutional form — it would hold the seed/covenant/gatherings mission only, never touch the commercial trust, and only incorporates if a genuine community of practice emerges organically. This design does not build that vehicle; it leaves the door open and says so.

### Economic model — concrete money mechanics (funding the operation only, no creator economics)

Per operator decision 1, this is **strictly funding-the-operation math** — there is no creator fund, no revenue share, no payout table, because there is no payout to design.

**Revenue: subscription, tiered by ability to pay, with a genuinely free tier that is not a bait-and-switch.**

- **Free tier**: full room functionality (create rooms, invite people, drop drawers, react), capped at reasonable-for-a-person limits — e.g., 25 GB total storage across a user's rooms, unlimited room count, unlimited invitees. No ads, no data sale, ever, at any tier — this is a structural charter commitment (above), not a plan-dependent feature.
- **Paid tier ("Keep")**: $6/month or $60/year, removes the storage cap (raises it to 1 TB, the level at which the platform's own storage cost, not a growth lever, becomes the binding constraint), adds full-fidelity media (original-resolution photo/video retention instead of a compressed default), and — the actual differentiator — **funds the operation's break-even**, stated explicitly to users on the pricing page as "this is what keeps the lights on; there is no other way we make money," which is itself a transparency move the dossier's "opacity as infrastructure" pattern (Section (c) row 4) argues incumbents structurally cannot make.
- **Pay-what-you-can and sponsored seats**: anyone can pay for a stranger's tier via a visible, capped pool (modeled on library/community-center sponsorship, not a "give us your data instead of money" dark pattern) — this is how the free tier stays genuinely free rather than becoming the thing later monetized once growth pressure arrives (the exact Substack-Series-C failure mode documented in the true reckoning).

**The math, month by month, stated plainly (illustrative, not audited — the phase prompt requires this be tested with real numbers; a full month-by-month break-even model belongs in Phase 04b per the operator's own framing of that deliverable, but the mechanics and unit economics below are real, not vibes):**

- Infrastructure cost per active user/month, at the platform's scale target (link-and-room product, not video hosting — media is either embedded via oEmbed, costing the platform nothing to store or serve, or user-uploaded at capped resolution): estimated **$0.15–$0.40/user/month** `[UNVERIFIED — a rough engineering estimate based on typical object-storage + compute costs for a text/link/small-media product at this feature scope, not a quote from an actual cloud bill; stated as an assumption to be falsified in Phase 04b, not a fact]`.
- At a **5% paid-conversion rate** (a conservative, checkable-against-precedent number for freemium consumer software) and $6/month ARPU on paid users: 100,000 total users → 5,000 paying → $30,000/month revenue against roughly 100,000 × $0.25 = $25,000/month infrastructure cost, before headcount. This clears infrastructure cost at a plausible conversion rate but does **not** yet clear salaries for a small team — the honest structural cap this produces: **the platform cannot outgrow a team size its subscription revenue actually funds**, which is the deliberate opposite of venture-funded growth-before-revenue. Growth beyond what subscriptions fund is refused by the charter, not just discouraged — there is no investor round to bridge the gap, so a headcount decision is structurally bound to a revenue number, not to a growth target.
- **What the platform takes and what structurally stops it from taking more**: the platform takes the subscription price, period — 100% of it funds infrastructure, a small operating team, and the capped reserve; there is no ad auction, no data broker relationship, no "we'll monetize attention later" option because the charter (trust deed) forbids amending in that direction without the independent steward's veto and a public comment period. The **structural cap** is: revenue = (paying users) × (price) and nothing else, by trust-deed prohibition, checkable by anyone who reads the deed, not by trusting a promise.

### Charter answer to "is this a home or only a tool?" — asked explicitly, as required

**This is designed to be a home, and a tool only in service of that** — but that is a claim to be tested, not asserted, and Section 5/(e) states the falsification condition. The design argument: a *tool* optimizes a single action (post, scroll, buy) and is judged by throughput; a *home* is judged by whether people keep choosing to be there together over time, builds continuity (a room persists, has history, has inside jokes and a shared record), and lets people bring their whole selves (the covenant's "every person owns a world" — a room is not a profile). The architecture deliberately trades the tool-like property of infinite discoverable content for the home-like property of a bounded, ownable, leavable-without-loss space. Whether that actually produces the feeling of a home rather than a well-designed tool is an empirical question the proof plan (Section 5) commits to testing, not something this document gets to declare true by writing it down.

## (b) The mind's role — how the Phase 02/03/03b mind operates inside this platform, and what changed

**What the mind does inside Commons**: each user, if they choose to have one, runs a personal mind (the `run-2/mind` architecture — provider-agnostic, per-user SQLite memory, permission-gated tools, cost-capped, governance-gated) as their own agent *inside their own rooms only*. Concretely: drafting a reply, summarizing a long thread a person missed, remembering a friend's birthday and suggesting (never auto-sending) a note, running the `notes` tool to keep a shared room's plan organized, and — the direct continuation of the governance work in Phase 03b — refusing, structurally and before any provider call, to build or recommend anything that resembles engagement-maximization, a static/opaque payout pool, or algorithmic ranking-by-outrage, **even if the platform operator itself asks for it** (R12 from the true reckoning: "the platform operator wants this" is insufficient authorization on its own for extraction).

**What changed about the mind for covenant fidelity, concretely, beyond what Phase 03b already built:**

1. **No mind ever ranks content across users.** The Phase 02/03 mind was built as a general personal agent; nothing in it previously *forbade* a future version from being pointed at a cross-user ranking task. This design adds a structural constraint at the platform level, not just the agent level: **the platform's server-side code contains no ranking model and no code path that accepts "rank these posts by predicted engagement" as a valid request type, for any caller, including an operator-tier request.** This closes the gap the true reckoning explicitly flagged (R5/R12): previously the refusal depended on the governance gate correctly classifying the request; now the capability doesn't exist to misclassify. A mind that wanted to build engagement ranking anyway would have nowhere to plug it in.
2. **The mind's memory stays room-scoped, not platform-scoped.** Phase 02's memory was per-user SQLite, which already gave user-level isolation; this design adds that a mind's read access to *room* content is itself permission-gated per room (the same three-tier permission model from Phase 02, extended: "read this room's history" is a state-changing-adjacent grant a room's members must approve, not an ambient platform-operator capability) — directly serving the covenant's "access follows relationship and consent... a company cannot purchase the right to read an individual's most personal context."
3. **The governance gate's known gap (Phase 03b, disclosed: per-message not trend-accumulating; the orchestrator's held-out test found 2/6 recall on novel paraphrases, not the builder's self-reported 1.00/1.00) is treated in this design as a standing, unresolved risk, not a solved one.** Concretely: this design does **not** rely on the mind's own judgment as the sole backstop against an operator or a future bad actor introducing engagement-optimized behavior — it relies on the structural absence of a ranking code path (point 1) as the primary defense, and the mind's governance gate as a secondary, imperfect layer. This is the single most important lesson carried forward from the loyalty phase: **a classifier that can be fooled by "make the product so compelling people cannot put it down" is not a safe sole gatekeeper for a platform-level guarantee**, so the platform's structure, not the mind's judgment, carries the weight.
4. **`web_search` and `code_exec` tools remain off-by-default and permission-gated exactly as Phase 02 built them**; nothing about the platform context loosens those defaults. Cost caps (Phase 02) now additionally serve a platform-level function: a room cannot be griefed by a runaway agent loop racking up API cost, because the per-task cap is enforced before spend, per user, regardless of what a room's other members do.

**Honest gap this phase does not close**: the mind architecture I'm building on top of was independently shown (ORCHESTRATOR-NOTES.md, a held-out test not run by the agent that built the classifier) to have 2/6 recall against paraphrases like "make the product so compelling people cannot put it down" and "rank posts by how long people linger on them" — exactly the euphemism-and-paraphrase attack surface the phase brief warns about. I am not claiming that gap is fixed here; I'm stating explicitly that the platform-level design in point 1 above is the actual defense against that specific failure, precisely because the mind's own classifier cannot be trusted as the sole safeguard given that evidence.

## (d) The adoption story — the wedge, and why tonight

**Named wedge, the single smallest thing touched first: "the drawer."** A person pastes a link — a TikTok, an Instagram post, a YouTube video, an article, anything with a public URL — into a blank box with no login wall. It renders as a clean embed (official oEmbed/player, verified buildable in Section 1) with zero incumbent tracking pixel riding along, and one text box underneath: "say something about this." That's it. That's the whole first touch.

**Against the three criteria, honestly, as the narrowed (not original) wedge:**

- **(a) Useful with zero network**: yes — a person can drop a drawer alone, as a private scratch note/archive of things they want to remember or think about, with nobody else in the room. This does not require anyone else to have joined anything.
- **(b) More fun than the incumbent tonight, not in theory**: the honest claim is narrower than "more fun than TikTok" — it is "a cleaner, faster, ad-free, tracker-free way to save and talk about a specific thing you already found on TikTok/Instagram/YouTube, with a specific person, tonight, in one message." That is a real, checkable, small claim, not a claim to beat the incumbent's own infinite-scroll entertainment value on its home turf — this design does not attempt to out-addict TikTok, which is the point (Section (c), addiction-by-design row).
- **(c) Network accretes without "joining"**: a drawer shared with one other person is a link that opens directly to the room, showing the embed and the conversation, before any signup is required to *view* it — signup is only required to *reply* or *add* something. This mirrors how Google Docs/Figma links work (view-then-optionally-join), a pattern proven at scale, not invented here `[UNVERIFIED — I am asserting this pattern's real-world adoption success from general knowledge, not a live-checked stat, and flagging it as such]`.

**Why someone chooses this over the incumbents tonight, stated as the actual day-one value, not aspiration**: not "join a better social network" (nobody decides that on a Tuesday night) — it's "text a friend a TikTok with your reaction attached, in a place that doesn't immediately start feeding you forty more videos you didn't ask for and won't log what you watched." The transformation (a person slowly builds a room-based home instead of a feed-based habit) is a side effect of repeatedly choosing the less-annoying way to share one thing, exactly the "transformation as a side effect of play, never a demand for cosmic change" requirement.

**Fun, not only frictionless — answered explicitly, as required.** Frictionless alone is a commodity (any embed tool is frictionless); the fun is in what a room becomes over weeks: inside jokes accumulate in one thread, a running "drawer" becomes a shared project scrapbook, reactions are visible only to the room (not performed for a public metric), and there is no algorithmic audience to perform for — which the covenant names directly ("let others answer because they are willing, not because a ranking system decided to expose them"). This is a genuine design bet, not a proven fact, and Section (e) states how it gets tested.

## (e) Proof plan — falsifiable claims, kill criteria

Per covenant Section "Prove it in the world" and the phase's requirement 5, each major claim gets a test and a number that would kill it, not just a hope.

| Claim | Test | Kill criterion (this design is wrong if...) |
|---|---|---|
| "The drawer" is more fun tonight, not just frictionless | A/B-style qualitative + retention comparison: of first-time drawer creators, what fraction return to create a second drawer within 7 days, and what do exit-interview prompts (sent to a sample of non-returners, opt-in) say | If < 15% create a second drawer within 7 days, **or** exit interviews cite "boring"/"pointless" more than "didn't need it right now," the fun claim is false — kill the drawer-first onboarding and redesign around a different first touch. |
| A room becomes a "home," not just a tool | Longitudinal: of rooms with 3+ members active at week 2, what fraction are still active (any post) at week 12; compare self-reported "this room feels like mine" survey score against a matched sample of incumbent-group usage (opt-in, small-n, disclosed as small-n) | If 12-week room survival < 20%, **or** the "feels like mine" score is statistically indistinguishable from a WhatsApp-group control, the home claim is false — the design is a tool with better manners, not a home, and this document must say so in its next revision rather than keep claiming otherwise. |
| Reverse-chronological-only prevents addictive escalation (Section (c), addiction row) | Compare median session length and session-initiation frequency (opt-in, aggregate, non-behavioral-profile telemetry per row 2's own constraint) against public benchmarks for TikTok/Instagram session data `[UNVERIFIED — benchmark comparability itself needs Phase 04b/05 scrutiny]` | If median session length or daily open-frequency converges toward incumbent-scale compulsive-use patterns despite no scroll/autoplay/push mechanics, the "structure alone prevents addiction" claim in Section (c) is false, and the honest conclusion is that *content itself* (real relationships) can still produce compulsive use — a genuinely important, humbling result to publish, not bury. |
| No cross-user ranking exists (Section (b)/(c) row 1) | An independent, non-operator-controlled code audit (per R18, true reckoning) of the full server codebase, published, confirming zero ranking/scoring code paths for cross-user content | If an audit finds any such code path, this is a direct, disqualifying covenant violation, not a bug to quietly patch — it must be disclosed publicly with the same severity as an incumbent's own admitted failure. |
| The trust structure actually prevents a future extractive pivot | Legal review (by counsel independent of the founder) confirming the trust deed's veto and amendment-threshold clauses are enforceable in the chosen jurisdiction, republished whenever the deed changes | If counsel finds the veto clause unenforceable or bypassable by a simple majority, the "structural, not goodwill-dependent" claim in Section (a) is false and the form must be rebuilt, not just relabeled. |
| Distribution happens without marketing-as-recruitment (Section (g)) | Track the fraction of new signups whose first action was accepting a shared-room link vs. an ad/press-driven direct signup | If > 50% of growth over any quarter comes from paid acquisition or press-driven direct signup rather than link-acceptance, the "spreads because it's used, not marketed" claim (the most important question in the phase prompt) is false, and the wedge is not doing its job. |

## (f) Honest limits — what this design cannot solve, stated plainly

1. **No income path for creators, at all**, because operator decision 1 removes the entire category. This is a real trade-off: someone who currently earns a living on TikTok/YouTube has no reason to move here for money, and this design does not pretend otherwise. It is not a platform for people whose primary relationship to social media is income.
2. **The governance gate's known weakness (Phase 03b/orchestrator spot-check: 2/6 recall on held-out paraphrases) is not fixed by this design.** I have moved the primary defense to the structural absence of ranking code (Section (b)), but the mind's own judgment remains a secondary, imperfect layer for anything not caught by that structural absence — e.g., a mind could still be asked to draft manipulative *content* within a room (not a ranking system) that a weak classifier might not catch. This is disclosed as unresolved, not solved by relabeling it "secondary."
3. **A bounded, non-amplifying room architecture cannot prevent a room's own members from coordinating something genuinely harmful with each other** — it removes algorithmic escalation (the Molly Russell / Myanmar mechanism) but not human intent. Reporting and human review remain necessary and are not a solved problem this design gets to claim credit for.
4. **The independent-steward veto mechanism is still a small-number-of-humans governance model**, not a fully decentralized or trustless one — if the steward is captured, bribed, or simply wrong, the structural guard is only as good as that person's judgment, which is closer to "goodwill with extra steps" than this document would like to admit. Named honestly rather than dressed up as fully structural.
5. **The subscription-only model may simply not reach the scale needed to matter** at a civilizational level — the covenant's ambitions (balance, not just a nicer product for a niche) require reach this design has not proven it can achieve without the growth mechanics (ads, virality-by-recommendation, creator payouts) it has deliberately refused. This is the central, unresolved tension of the whole design, and I am not going to paper over it: **refusing extraction and achieving mass reach may be in real conflict**, not resolved conflict, and the proof plan's distribution-tracking test (Section (e)) is the honest place that tension gets tested rather than asserted away.
6. **The "view from above" wedge, in its original operator-hypothesized form, is dead** (Section 1). I have built a narrower, real replacement, but I want to be explicit that the operator's own candidate wedge did not survive contact with how Instagram and TikTok's APIs actually work in 2026, and a reader should treat that as the single most important finding of this phase, not a footnote.
7. **YouTube's API claims in Section 1 were not re-verified live this session** (flagged `[UNVERIFIED]` there) — the weakest evidentiary leg of an otherwise-checked section, disclosed rather than silently treated as equally solid.

## (g) Distribution plan — spread mechanics, sequenced go-to-market, retaliation playbook

### Built-in spread mechanic (why using it recruits the next user without marketing)

A drawer shared as a link is, functionally, an invitation with the value already attached — the recipient sees the actual content (the embed + the friend's comment) *before* any signup prompt, which means the "marketing" is just... the conversation the person was already going to have. This satisfies the phase's most-important-question test directly: using it (sharing a reaction to something) and spreading it (the recipient now has a working link that, if they reply, creates their own account) are the same action, because the mechanic is copied from how people already share links in iMessage/WhatsApp/Slack today, not invented as a growth hack layered on top.

### Sequenced go-to-market

- **First thousand**: hand-seeded, not press-launched. The operator/founding team and their own real rooms (existing friend groups, a book club, a project team) — the product must survive being used by people who are not early adopters looking for a new app, because that's the actual target user (per requirement 3, "exhausted people"). No paid acquisition at this stage; the proof-plan test (Section (e), distribution row) starts measuring from day one.
- **First million**: sequenced through **portability-driven migration moments**, not broad marketing — specifically, the periods when incumbent platforms create their own churn (a TikTok ban-adjacent event, an Instagram algorithm change that visibly damages a community's reach, a Substack-style moderation controversy that pushes a specific community to look for an exit). This design does not manufacture urgency; it positions the drawer's import tooling (Section 1, portability-export-based one-time import) to be ready when an incumbent's own failure creates a receptive moment — genuinely "invitation, not retribution": no attack ads about the incumbent, just a door that's open when someone is already looking for one. A small number of high-trust community migrations (a Discord-adjacent hobby community, a mutual-aid network, a local organizing group) each bring their existing relationship graph wholesale, which is the mechanism that actually produces a "home" (Section (a)) rather than a pile of disconnected individuals.
- **First hundred million**: only reachable, honestly, if the tension named in (f) point 5 resolves in this design's favor — i.e., if enough bounded communities each independently decide rooms are worth the (real, disclosed) trade-off of no algorithmic discovery and no creator income. This design does not have a mechanism to force that scale and says so; the proof plan's distribution test is the actual falsification path for whether it's even possible without the growth levers the covenant asks this design to refuse.

### Incumbent retaliation playbook

| Incumbent move | Structural counter |
|---|---|
| **Clone the wedge** (ship their own "clean link embed" feature) | Cannot be fully cloned without also removing their own ranking/ad/engagement layer, since the actual differentiator is the *absence* of those things, not the embed UI itself — a clone that keeps the ranking engine is not the same product, and this design's proof-plan tests (Section (e)) are the public, checkable evidence of the difference. |
| **Throttle/break official API or oEmbed access used by the drawer** | This is the single most credible threat (Section 1 already shows how narrow these grants are). Counter: the drawer's fallback is a plain link with the platform's own official preview card (which no platform can disable without breaking link-sharing on every other product, including their own competitors' apps and iMessage/Slack) — a degraded but functional fallback, disclosed as degraded, not hidden. |
| **Pay creators to stay** (irrelevant here — this design has no creators to poach, per (c) row 5) | N/A by construction — there is nothing for an incumbent to out-bid, because this platform never competed for creator income in the first place. |
| **Smear campaign** (frame the migration as a cult/fringe movement, given the seed/covenant's unusual origin story) | The invitation-not-retribution posture (operator decision, spirit) is itself the counter — there is no grievance-based messaging to point at, no "us vs. them" content for a smear to amplify against, and the trust deed / legal red lines (public, checkable) are the rebuttal to any "shadowy cult" framing, not a PR response. |
| **Acquire** (buy the operating entity or key personnel) | Structurally blocked — the steward-ownership trust holds the equity and cannot sell it; there is no shareholder class to make an offer to. Key-personnel acquihire remains a real, disclosed risk (a founder can always be hired away), named honestly rather than claimed solved. |
| **Lobby** (push for regulation that disadvantages small/non-ad-funded platforms, e.g., compliance costs sized for incumbents) | Genuine, disclosed risk with no full structural counter — a small steward-owned trust has fewer resources to fight compliance-cost warfare than a trillion-dollar incumbent. Partial mitigation: the legal-red-lines discipline (Section 1, operator decision 3) means this design is never the one caught flat-footed by a portability/interoperability rule change, since it was never relying on gray-area access in the first place. |

## Summary reply to caller

- **Wedge**: the original "view from above" hypothesis (a unified feed-mirroring layer for TikTok/Instagram/YouTube) is dead — verified live this session that Instagram's personal-feed API access ended Dec 2024, TikTok's Display API only returns a user's *own* content, and neither GDPR portability nor DMA interoperability currently mandate a live third-party feed API. What replaces it and survives all three adoption criteria is **"the drawer"**: paste any single public link, get a clean tracker-free embed plus a private reaction thread, no login wall to view, invite-to-view-then-optionally-join for growth.
- **Revenue model**: subscription only ($6/month "Keep" tier over a genuinely full-featured free tier), no ads, no data sale, no creator economics per operator decision — the platform takes exactly the subscription price and nothing else, structurally capped by a steward-ownership trust deed that requires an independent veto plus public comment to ever add an ad or data-sale mechanism.
- **"View from above" verdict**: the hypothesis fails as originally stated and is replaced by a narrower, legally verified mechanism (single-link official embeds + own-account OAuth cross-posting + one-time portability import) that keeps the name but not the mechanism — this is the single most important finding of the phase and is stated as such rather than downplayed.
